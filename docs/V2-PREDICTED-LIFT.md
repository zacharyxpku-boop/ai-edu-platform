## 整体预测

- **v1 通过率**：约 **70-78%**（13 + 2 = 15 case，v1 必 fail 2 个新分支 + ~3 个边界 case）
- **v2 通过率**：约 **88-95%**
- **绝对 lift**：**+15-20 个百分点**

## 数据回来后的动作矩阵

### 情况 A：v2 ≥ v1 + 10pp（接近预测）
切默认 PROMPT_VERSION=v2，archive v1 prompt 为 buildSystemPromptV1。
单 commit。无回滚。

### 情况 B：v2 ≥ v1 但 < +10pp（v2 没明显赢）
**不切**。深挖原因：
- 是不是 5 行上限把"分式计算"反而压死了？看 case#4 长度。
- 是不是「自称切老师」让 Hint 强档过于权威？看 case#4b 输出。
- 选 1-2 处 v2 失分点反向调整，再跑一次。

### 情况 C：v2 < v1（反向退化）
**红线**。立刻：
1. revert buildSystemPromptV2 路由（保 v1 默认）
2. 把 v2 函数留着但不接路由
3. 写 docs/V2-FAILURE-AUDIT.md 列每个 v2 失分 case 的具体原因
4. 决定是 v2 路线本身错了（去拍其他方案），还是只是文案细节没调好

### 情况 D：v2 在 2 个新 case 上没拿满（fail 任一）
**严重信号**。说明状态机分支没真传到模型行为。
- 检查 buildSystemPromptV2 line 146-148 是否在 system_messages 里被组装进 LLM 输入
- 看 trace 实际发给 DeepSeek 的完整 messages 数组
- 不是 prompt 的问题，是路由代码的问题

## 反作弊条款

数据回来后**不允许的解读**：
- ❌「v2 通过率 80%，比 v1 75% 高 5pp，达到了预期下限」（80 ≠ 88-95 预测，差 8-15pp 是没达预期，不能用「下限」字眼粉饰）
- ❌「v2 在某个 case 比 v1 低，但其他 case 高，整体平衡」（只看整体不看分布是数据丢失）
- ❌「v2 失败的 case 是 prompt eval 用例本身有问题」（case 是 v2 写完之前定的，不能事后改 case）

允许的解读：
- ✓「v2 通过率 X%，v1 Y%，差 Z pp，落入情况 [A/B/C/D]，按矩阵执行」
- ✓「2 个新 case，v1 0/2，v2 N/2，N=2 符合预期，N<2 触发情况 D」
