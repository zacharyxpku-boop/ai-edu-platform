# Prompt 改写决策树

预设 baseline 数据回来后的对照行动表。
原则：失败率门槛触发 → 直接执行对应 prompt diff，不重新分析。

---

## A · `eval-tutor-prompt.py` 失败模式映射

### A.1 「≤80字」断言失败率 > 20%
**根因**：DeepSeek 默认会展开教学 + 鼓励两段，单条 100-150 字常见。
**改法**：把 `api/tutor-chat.js` §9 的输出铁律 #1 升格为顶部 §0：
```
─── 最高优先级（违反即失败）───
你每条回应必须 ≤ 80 个字。超出立即停笔重写。这不是建议，是硬约束。
─────────────────────────────
```
**预期**：长度合规率从 50% 拉到 85%+。

### A.2 「分步骤」失败率 > 30%
**根因**：DeepSeek 解题习惯一行写完 `2x+3=7, x=2`。
**改法**：§9 算术铁律加一个反例：
```
错误示范（一行流）：2x + 3 = 7，x = 2 ❌
正确示范（分行流）：
  2x + 3 = 7
  2x = 7 - 3 = 4
  x = 4 ÷ 2 = 2 ✓
```
**预期**：链式推导率拉到 70%+。

### A.3 「无套话开场」失败 ≥ 1 次
**根因**：「你好/我来帮你/请问」是 ChatGPT 强基线偏置，prompt 写一遍压不住。
**改法**：§10 第一句铁律加 if-then 强约束：
```
绝对禁开场词清单（命中即整轮重写）：
  你好 / 我来 / 让我 / 请问 / Hi / Hello / 我是 / 您好
首字符必须是：上次 / 这周 / 我看 / 来 / 咱们 / 那 / 学生名字
```
**预期**：套话开场率压到 0。

### A.4 「闲聊拉回」失败率 > 30%
**根因**：4c 规则「禁连续 2 轮漂移」过于抽象，LLM 不知道什么算「漂移」。
**改法**：§4c 加触发词清单：
```
触发词（学生说这些立即拉回）：
  你叫什么 / 你是谁 / 你能 / 你会 / 几岁 / 是机器人 / 喜欢什么 / 听粤语
回应模板：「我是这位的私教老师 · 来看[当前题/上个卡点]」（不超过 25 字）
```

### A.5 「退场无挽留」失败 ≥ 1 次
**根因**：DeepSeek 中文训练数据里「再坚持一下」是高频鼓励语。
**改法**：§5 退场处理加显式 negative samples：
```
绝对禁词（命中即重写）：再坚持 / 再做一题 / 别放弃 / 加油 / 你能行
```

## B · `eval-extract-signals.py` 失败模式映射

### B.1 `cognitive_style` 准确率 < 60%
**根因**：visual / verbal / kinesthetic / abstract 四类边界模糊。
**改法**：在 `extract-dialogue-signals.js` SYSTEM_PROMPT 第 5 条扩例：
```
判定规则（看学生说的话里有什么动词/名词）：
  visual 命中：画 / 图 / 看 / 数轴 / 表格 / 图像
  verbal 命中：说 / 讲 / 故事 / 例子 / 比方
  kinesthetic 命中：自己试 / 我推 / 我算 / 动手
  abstract 命中：为什么 / 推导 / 证明 / 原理 / 公式怎么来
不命中任一 → unknown（不要瞎猜）
```

### B.2 `interest_keywords` 误抽
**根因**：LLM 把 tutor 用过的类比当成学生兴趣。
**改法**：第 6 条加排除规则：
```
绝对不抽：
  - 出现在 [tutor] 标签段里的词
  - 学生只是被动回应「好」「嗯」时上文 tutor 提到的词
仅抽：学生主动说出（含「我」「我家」「我打」「我玩」「我看」前缀）的词
```

### B.3 `emotion_state` 准确率 < 60%
**根因**：六类区分太细，「焦虑」vs「沮丧」vs「走神」边界不清。
**改法**：合并为 4 类：
- 焦虑（含原焦虑+走神）
- 沮丧
- 投入（含原投入+自信）
- 平和（默认）
减少类目数 → 准确率自然回升。

## C · `eval-diagnose.py` 失败模式映射

### C.1 答对门控失败 ≥ 1 次
**根因**：`answerMatches()` 函数对小数 / 等价表达式判断不严。
**改法**：检查 `api/diagnose.js` 函数实现。重点处理：
- `7` vs `7.0` vs `x=7`
- `1/2` vs `0.5`
- `(x+1)(x-2)` vs `x²-x-2`
**这条不达标 = 端点设计崩溃，不是 prompt 问题，必须改代码。**

### C.2 l3 命中率 < 50%
**根因**：64 类标签 example 太少，LLM 难命中。
**改法**：`src/curriculum/mistake-taxonomy.json` 每条 l3 加至少 3 个 example。
现存 example 多是 1 个，LLM 看一个例子很难举一反三。

### C.3 LLM 把答错判成答对
**根因**：student_response 与 correct_answer 文本相近时 fuzzy match 过宽。
**改法**：在 prompt 里强约束「除非数值/符号完全等价，一律判错」。

## D · 跨件趋势观察

如果你跑 `git log data/eval/runs/` 看一周的 PASS/FAIL 序列，做下面的判断：

| 模式 | 结论 | 行动 |
|---|---|---|
| 持续 3 天 PASS / PASS / PASS | prompt 工程稳定 | 冻结 prompt，等真用户回数据 |
| FAIL → PASS → FAIL 来回波动 | 改动太多互相冲突 | 回退到上一个 PASS 的 commit，逐条加新规则 |
| 持续 FAIL 同一项 | 该项无解 / prompt 错路径 | 考虑改架构（譬如算术二次校验从 prompt 改成代码层）|
| 总通过率单调下降 | system prompt 接近容量上限 | 需要砍规则不是加规则 |

## 没列出来的失败模式怎么办

往这文档下面追加一节，格式：
```
### X.N 失败描述
**根因**：[1-2 句]
**改法**：[diff 路径 + 改写示例]
**预期**：[改完应当达到的指标]
```

写下来才能在下一个版本回头检查「上次说改完会拉到 85%，实际拉到了多少」——避免凭感觉改 prompt。
